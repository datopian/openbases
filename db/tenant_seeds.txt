# Migrations that seed Datopian's own records rather than schema.
#
# `workgraph-migrate --fresh` records these as applied WITHOUT running them, so
# a new deployment comes up with the schema and none of our data. It refuses
# unless the database is empty, so it can never skip a migration on a running
# deployment. Datopian's own databases are unaffected: these are already
# applied there, and cmd/migrate still verifies their checksums.
#
# Every file here must contain no DDL, which cmd/migrate's tests assert.
#
# Several other migrations contain `INSERT INTO` against the same tables and are
# NOT in this list, correctly: those statements sit inside CREATE FUNCTION
# bodies and run when the function is called, never when the migration is
# applied. 0084 registers a rig, 0027 registers a cell.
#
# A `DO $$ ... $$` block is the opposite and the distinction is easy to lose: it
# executes immediately, so an insert inside one IS a seed. 0080 seeds through
# one and belongs here. Both guards -- cmd/migrate's test and
# scripts/check_disclosure.py -- strip function bodies and KEEP DO blocks.
#
# This list was wrong in both directions when it was first written, which is
# recorded because the errors are instructive:
#
#   0027 and 0052 were IN it and seed nothing. They define functions with
#   `CREATE OR REPLACE FUNCTION`, and the test meant to catch that matched only
#   `CREATE FUNCTION`. Skipping them removed system_register_execution_node,
#   system_register_execution_cell, system_attach_project_to_cell and
#   system_record_usage from every fresh install -- an install that came up
#   looking clean and could not register a node.
#
#   0018 and 0028 were MISSING and seed credential_registry at the top level,
#   ten Datopian addresses among them. The assertion did not cover that table,
#   so "every tenant table is empty" was measured against an incomplete list.
#
# Both were found by cross-checking this list against
# scripts/disclosure_baseline.txt, which flagged different files. Two guards
# disagreeing is worth more than either agreeing with itself.
#
# Do not add to this list to make a new seeding migration acceptable. A record
# about the real world belongs in the deployment's database, put there by an
# install step; scripts/check_disclosure.py refuses it in a migration.
